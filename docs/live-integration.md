# 실제 Groq 페이지 생성 연동 검수

## 범위와 실행

2026-10-16 15:45 KST에 사용자가 허용한 실제 Groq 연동 검수를 실행했다. `scripts/live-page-jobs-smoke.ts --allow-live`는 가상 도서관의 합성 페이지 네 개와 별도 SQLite만 사용한다. 원본 Manyfast에는 접근하거나 요청하지 않았고, 실제 사용자 프로젝트는 읽거나 변경하지 않았다. 환경 키는 서버의 환경 로더와 `GroqProvider`에서만 사용했다.

기본 계획은 실제 호출 4회이며 실행당 하드 상한은 6회, 응답 한도는 호출당 3,000토큰이다. 자동 테스트에는 포함되지 않는다. 자연 발생 제공자 오류가 한 번 발생하면 이후 실제 호출을 차단한다. 인증·사용 한도 오류에 대한 자동 재시도는 없다.

실행 명령:

```powershell
npx tsx scripts/live-page-jobs-smoke.ts --allow-live
```

최초 중단 결과는 `.qa-data/live-page-jobs-1792133123137/report-initial.json`, 명시적 재개까지 포함한 최종 결과는 같은 디렉터리의 `report.json`에 보존되어 있다. `smoke.sqlite`에는 합성 프로젝트와 작업 기록, `synthetic-project.json`에는 최종 화면이 저장된다. 이 디렉터리는 Git에서 제외된다.

## 관찰 결과

설정 모델은 `openai/gpt-oss-120b`였다. 최초 실행은 두 번 성공한 뒤 세 번째 요청이 `AI_RATE_LIMIT`으로 거절되어 중단했다. 이후 별도의 명시적 재개 지시에 따라 기존 데이터베이스의 실패 작업만 한 번 재시도했다. 누적 실제 요청은 5회이며, 성공 4회와 최초 사용 한도 거절 1회다. 최종 계획 검증은 모두 통과했다.

| 실제 호출 | 목적 | 결과 | 경과 시간 |
|---|---|---|---:|
| 1 | append의 도서 검색 페이지 | 성공, 서버 스키마·참조 검증 통과 | 2,890ms |
| 2 | 실패한 예약 확인 페이지만 재시도 | 성공, 서버 스키마·참조 검증 통과 | 2,519ms |
| 3 | 기존 도서 검색 페이지 regenerate | 사용 한도 오류 `AI_RATE_LIMIT` | 157ms |
| 4 | 명시적 재개: 실패한 도서 검색 작업만 재시도 | 성공, 부분 승인 검증 완료 | 2,599ms |
| 5 | 취소 시나리오의 대출 현황 페이지 | 성공, 다음 페이지의 실제 호출 없이 취소 | 2,946ms |

토큰 사용량과 비용은 확인할 수 없다. 현재 `GroqProvider` 반환값에는 usage가 노출되지 않으므로 0으로 기록하거나 추정하지 않았다. 3,000은 실제 사용량이 아니라 응답 상한이다.

첫 append에서 예약 확인 페이지의 첫 시도는 **실제 제공자 호출 전에 검수 코드가 명시적으로 실패시켰다**. 이는 Groq 장애나 실제 응답 실패가 아니다. 첫 페이지의 실제 성공 결과를 보관한 상태에서 실패한 페이지 작업 ID만 재시도했다. 해당 재시도가 두 번째 실제 호출이다. 첫 번째 성공 작업의 상태, 응답, 화면 데이터는 재시도 전후 완전히 같았다.

다음 항목은 실제 생성 결과와 제품 API를 연결해 확인했다.

- 승인 전 프로젝트의 데이터와 버전은 변경되지 않았다.
- 부분 성공 제안이 생성되었고, 실패한 페이지만 재시도할 때 이전 제안은 취소 상태가 되었다.
- 기존 성공 작업을 다시 호출하지 않고 두 번째 작업만 성공으로 전환했다.
- 최종 전체 승인으로 별도 화면 버전이 생성되었으며, 원본 화면 버전은 빈 상태를 유지했다.
- 생성 화면 두 개와 결과 프로젝트가 서버 스키마를 통과했다.
- 자연 발생 사용 한도 오류 후 다른 페이지에 실제 요청을 보내지 않았다. 실패한 regenerate는 새 제안이나 결과 버전을 만들지 않았다.
- 명시적 재개에서 첫 append의 성공 결과를 그대로 재사용했다. regenerate의 실패 작업만 재시도하고, 다른 페이지는 다시 호출하지 않았다.
- regenerate에서 한 화면은 실제 Groq 응답으로 성공시키고 다른 화면은 제공자 호출 전에 명시적으로 실패시켰다. `allowPartial` 없는 승인은 거부됐으며, 명시적인 부분 승인으로 새 버전을 만들었다. 실패한 기존 화면과 원본 버전 전체가 동일하게 보존됐다.
- 다음 append에서 한 화면이 실제 생성·검증된 후 두 번째 페이지를 제공자 호출 전 대기 지점에서 취소했다. 완료한 화면을 보존했고, 아직 호출하지 않은 페이지는 실제 Groq 요청을 보내지 않았다.
- 임시 서버와 SQLite를 다시 열어 취소 상태와 완료 결과가 유지되는 것을 확인했다. 명시적인 제안 준비 및 부분 승인에는 추가 Groq 호출이 없었다. 기존 원본 화면 두 개를 보존한 결과 버전에 성공한 화면 하나만 추가됐으며, 취소한 페이지는 추가되지 않았다.

## 최초 중단과 명시적 재개

최초 실행의 사용 한도 응답은 약 3초 후 재시도를 안내했으나 스크립트가 자동으로 다시 요청하지 않았다. 별도 재개 지시를 받은 15:47:47 KST에 다음 명령을 실행했고, 15:47:54 KST에 남은 검증이 끝났다.

```powershell
npx tsx scripts/live-page-jobs-smoke.ts --allow-live --resume .qa-data/live-page-jobs-1792133123137
```

재개는 최초 성공한 append 두 호출을 반복하지 않았고, 누적 호출 상한 6회를 유지했다. 두 번째 사용 한도·인증 오류가 발생했다면 다시 재시도하지 않고 중단하도록 진행했다. 실제로는 추가 두 호출이 성공했다.

## 해석의 범위

실제 모델이 만든 합성 화면과 제품의 검증·제안·승인·보존·재시작 흐름을 함께 검사한 결과다. 의도적으로 넣은 페이지 실패와 제공자 호출 전 취소 대기 지점은 검수 장치이며, 실제 Groq 장애 또는 진행 중 네트워크 요청 취소를 재현했다는 뜻은 아니다. 모델의 일반적인 디자인 품질이나 원본 서비스와의 시각적 일치도를 검증한 결과로 확대해 해석하지 않는다. 이 작업에서 제품 소스나 원본 서비스는 변경하지 않았다.
