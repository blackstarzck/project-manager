# Shared implementation contract (2026-10-16)

## Phase 2 additions — nested screens and independent versions

`Project.flowGroups` contains named groups and version objects (`id`, `groupId`, `name`, `number`, timestamps, `revision`, `flowRevision`, `wireframeRevision`, `flow`, `wireframes`). `selectedFlowVersionId` identifies the active version; existing top-level `flow`, `wireframes` and their artifact revisions remain its projection. Legacy projects are wrapped in a default group/v1 without changing document IDs or revisions. Copied versions keep entity IDs, while version IDs isolate their state. Project duplication and backup import remap the entire graph.

- GET `/projects/:id/flow-groups` returns groups.
- POST `/projects/:id/flow-groups` accepts `{name, expectedRevision, sourceVersionId?}`; blank by default or copies the source into a new group.
- POST `/projects/:id/flow-groups/:groupId/versions` accepts `{name?, sourceVersionId?, expectedRevision}`; creates and selects a blank or copied version.
- POST `/projects/:id/flow-versions/:versionId/select` accepts `{expectedRevision}`.
- PATCH `/projects/:id/flow-groups/:groupId` and `/projects/:id/flow-versions/:versionId` accept `{name, expectedRevision}`.
- Version mutations return the complete Project. Save and AI requests for flow/wireframes include `flowVersionId`. Old-context requests return 409. Proposal context mismatches leave the proposal pending so the user can select its original version and review it there.
- Exports optionally accept `flowVersionId` to read an inactive version without selecting or changing it. Backups include all versions. Reference validation includes inactive versions.
- Project revision restoration preserves current independent version history and adds historical flow/screens as a new version. Restoration of global features may be rejected if it would break references in preserved versions.

`WireElement` retains `id`, `type`, `text`, `targetScreenId`. Optional `children` recursively contain full elements, with at most 8 levels and 500 elements per screen. Containers: row, column, grid, box, card, header, sidebar, body, footer, modal. Table uses `columns` and `rows`; spacer reserves space. Optional `style` only permits bounded numeric geometry, enums and hex/transparent colors. Executable HTML/CSS/scripts are not accepted.

Actions are navigate (`targetScreenId`), back, openModal (`targetElementId` on the same screen) and closeModal. Null targets are valid unfinished configuration; supplied references must resolve. Deleting a screen clears nested incoming links and clears per-screen undo history so deleted links cannot be resurrected. Layer editing, reparenting and sibling ordering preserve opaque IDs. Desktop uses a 1440×900 minimum canvas and mobile 390×844, fitted with explicit zoom. Preview and offline HTML render the nested structure and navigation. PNG captures the unscaled canvas.

AI panel geometry is stored locally with a versioned schema: docked width 432px; floating default 412×640; bounded resizing, drag/keyboard movement, viewport clamping and recovery. Dock/floating changes keep one mounted panel instance and retain its composer and run state. Panel geometry contains no API key. All generation still uses the server-side Groq provider and explicit user requests.

Root owns shared/schema.ts, package/configs, docs except qa-loop. Backend owns server/**. Frontend owns src/**. QA owns tests/** and docs/qa-loop.md. Request contract changes before editing shared files.

## Phase 3 — explicit AI flow destinations

`FlowGenerationMode = 'edit' | 'new-version' | 'new-group'` is exported from `shared/schema.ts`, together with `flowGenerationModeSchema`. POST `/api/projects/:id/ai/runs` now accepts `{artifact, prompt, entityIds?, model?, flowVersionId?, flowGenerationMode?}`. The mode is optional for backward compatibility: an omitted mode on a flow request means `edit`. Supplying any mode for a non-flow artifact is rejected with HTTP 400 `INVALID_FLOW_MODE`. Nonempty `entityIds` are allowed only in edit mode; new-version/new-group requests generate the entire graph and reject a selected-item scope with HTTP 400 `INVALID_SELECTION`.

`AiRun.flowGenerationMode?` and `Proposal.flowGenerationMode?` preserve the chosen mode. Retry reuses mode, prompt, entityIds and originating flowVersionId. Older stored runs/proposals without a mode keep edit behavior. `Proposal.resultFlowVersionId?` is set only after a new destination has been approved and committed; it identifies the result, while `flowVersionId` continues to identify the origin.

| Mode | Provider context | Approval result |
|---|---|---|
| edit | Current active flow and project context | Apply the proposed graph to the originating version, using the existing flow revision check. |
| new-version | Originating flow, global PRD/features/settings; no prior wireframes or flow-group history | Append the next numbered version to the origin's group, select it, and start it with no wireframes. |
| new-group | Global PRD/features/settings with an empty flow and no wireframes or flow-group history | Create a fresh group and first version, select it, and start it with no wireframes. |

New modes always produce one pending aggregate flow change, even if the graph is identical to the source or empty. They create no group/version during request start, streaming or proposal preparation. Rejection, provider/schema failure and cancellation leave project data and version counts unchanged. A blank source is valid for either mode. New group/version IDs are fresh UUIDs; graph entity IDs are scoped to the version and may remain stable between related versions.

Approving that single change creates its destination, validates references against the latest global features, commits the project snapshot and audit, records proposal resolution/resultFlowVersionId, and stores the idempotency command in one SQLite transaction. Repeated approval with the same command or a new command creates no additional version. New group names use the first line of the AI summary, trimmed to 120 characters; generated versions in an existing group are named `AI 수정본 N`. Existing rename actions remain available.

The selected version must still equal the originating flowVersionId for approval. A wrong selection returns HTTP 409 `FLOW_CONTEXT_CONFLICT` and leaves the proposal pending so the user can return to its origin. A changed origin flow revision returns HTTP 409 `REVISION_CONFLICT`; the proposal is conflicted and can be regenerated. Existing origin flow/screens, including later manual screen changes, are preserved when creating a new result. Generated graph validation does not require source screens to reference the new graph: old screens remain with their old version, while the new version has an empty screen array. Invalid latest feature references fail the whole approval without creating an empty destination.

Approval timing is Planit's independent design. Public Manyfast client evidence establishes separate generate/regenerate destinations and optimistic state, but does not establish equivalent approval or server transaction semantics. Phase 3 does not introduce group/version deletion, separate wireframe-version history, or tablet mode.

Related backend validation: 9 new generation-destination cases plus the existing app/version suites passed (24 cases). Coverage includes preserved origin bytes, removed source page IDs, empty/identical graphs, rejected/failed/cancelled work, version-context return, source revision conflicts, current feature-reference rollback, pending/applied persistence and idempotency. These injected-provider tests do not claim actual Groq output quality or original-service fidelity; independent browser QA and real smoke reports remain separate.

## Phase 4 — independent wireframe history and reversible archives

Each `FlowVersion` now owns `wireframeVersions: WireframeVersion[]` and `selectedWireframeVersionId`. A wireframe version has `id`, `flowVersionId`, `name`, `number`, `createdAt`, `updatedAt`, `archivedAt`, `revision`, `wireframeRevision`, and `wireframes`. `Project.selectedWireframeVersionId` mirrors the selected flow's selection. Top-level `wireframes` / `artifactRevisions.wireframes` and the selected flow's legacy `wireframes` / `wireframeRevision` remain projections of the selected wireframe version. These projections preserve existing editors and export contracts; modifying them updates only that selected history entry. Global PRD/features and a flow graph remain shared by all wireframe versions under that flow.

Legacy projects receive one wireframe version per flow without changing screen IDs, nested IDs, entity revisions, flow revisions, or wireframe artifact revisions. Migration persists the new IDs once (`PRAGMA user_version=3`). Old wireframe runs/proposals without a wireframe context bind to their originating flow's migrated selected wireframe version during startup. The binding is persisted before later selections can change it. Interrupted runs still fail safely on restart without retrying the provider.

All paths below have the `/api` prefix:

| Endpoint | Body / result |
|---|---|
| GET `/projects/:id/flow-versions/:flowVersionId/wireframe-versions` | All wireframe versions, including archived entries. |
| POST the same path | `{expectedRevision, name?, sourceWireframeVersionId?}`; creates/selects a blank version or copies exactly one source snapshot. HTTP 201 Project. |
| POST the same path plus `/:wireframeVersionId/select` | `{expectedRevision}`; atomically selects the owning flow and wireframe version. HTTP 200 Project. |
| PATCH the same path plus `/:wireframeVersionId` | `{expectedRevision, name}`; renames without changing artifact revisions. HTTP 200 Project. |

Manual wireframe copies have fresh version IDs and retain scoped screen/element IDs. Manual flow copying copies all active wireframe histories from the source, remaps their version/parent IDs, and preserves source selection; it excludes individually archived wireframe versions. Project duplication and backup import preserve all histories and archive states while remapping every group/version/screen/nested action reference. Whole-project revision restore preserves current histories and creates a separate flow version containing a new wireframe version from the historical selected screen snapshot. If the historical group is archived, the restored version is placed in the currently active group. Restoring global PRD/features still fails atomically if preserved inactive or archived histories would have dangling references.

Wireframe artifact saves and AI requests carry both `flowVersionId` and `wireframeVersionId`. Missing context is accepted only when the corresponding history has one version; otherwise HTTP 409 `FLOW_CONTEXT_REQUIRED` or `WIREFRAME_CONTEXT_REQUIRED`. Wrong selected contexts return `FLOW_CONTEXT_CONFLICT` or `WIREFRAME_CONTEXT_CONFLICT`. Even copied versions with identical screen IDs and revision numbers cannot accept another version's save or approval. Validation checks page, feature, screen and recursive modal/navigation references across every history, including inactive and archived versions. Removing a page still referenced by historical screens is rejected; the client exposes the dependent history rather than leaving an unsaveable edit.

`WireframeGenerationMode = 'edit' | 'append' | 'regenerate'` is exported from shared/schema. AI start accepts optional `wireframeGenerationMode` and `wireframeVersionId`; supplying a wireframe mode on another artifact is HTTP 400 `INVALID_WIREFRAME_MODE`. Omitted mode means `edit`. Runs/proposals persist mode and originating wireframe ID. Retry preserves both context IDs, mode, prompt and entityIds.

| Mode | Scope | Approval |
|---|---|---|
| edit | Existing per-screen changes; optional selected screen IDs or flow page IDs. | Apply to the originating wireframe version using entity revisions and existing dependent-subset validation. |
| append | Only flow page IDs with no source screen. Empty entityIds resolves to all missing page IDs at start; no missing pages is HTTP 400 `INVALID_SELECTION`. Provider must return fresh screen IDs in the captured scope. | Preserve every source screen and create/select a new wireframe version containing the additions. |
| regenerate | Existing screen IDs, including unlinked manual screens, or flow page IDs. A nonempty scope preserves all unselected source screens byte-for-byte. Empty scope replaces the complete screen set. | Create/select a new wireframe version; the origin history entry remains unchanged. |

Append/regenerate create exactly one aggregate pending `Change` (`artifact: 'wireframes'`, `entityId: 'wireframes'`, before/after screen arrays), even for identical regeneration output. Approval is atomic for the full destination, so there is no partially created screen version. Generation, rejection, cancellation and invalid provider output create no destination. `baseWireframeRevision` and `baseFlowRevision` bind the complete copied source and its graph: changing either after generation returns HTTP 409 `REVISION_CONFLICT`. Selecting another version returns context 409 while keeping the proposal pending; returning to its original context permits approval if revisions still match. `resultWireframeVersionId` is recorded only when approval creates the destination; `wireframeVersionId` continues to mean the origin. Repeated approval creates no duplicate history. The name is the first AI-summary line, capped at 120 characters, with an editable fallback name.

Archives use `archivedAt` on groups, flow versions and wireframe versions. POST `/projects/:id/flow-groups/:groupId/archive|restore`, `/projects/:id/flow-versions/:versionId/archive|restore`, and the nested wireframe version path plus `/:wireframeVersionId/archive|restore` all take `{expectedRevision}` and return Project. These operations never hard-delete content. Archiving the final active group, flow version in a group, or screen version in a flow returns HTTP 409 `LAST_ACTIVE_VERSION`. Archiving a selected entry selects its highest-number active sibling; group fallback uses the latest-created active group (ID tie-break), then its highest-number active flow. The owning flow remembers its selected wireframe version.

Restoring clears only the requested entry's archive marker and keeps the current selection. Restore parents before children. Parent archive leaves child archive markers unchanged, so restoring a group does not revive individually archived descendants. Saves, starts, approvals, selection and source-copy operations targeting an effectively archived origin return HTTP 409 `VERSION_ARCHIVED`. An in-flight generation may finish as a pending proposal, but cannot apply until the origin is restored and selected; this error does not permanently conflict the proposal. Archived history remains readable/exportable and participates in reference validation. Rename is permitted for archived history.

Exports accept `flowVersionId?` and `wireframeVersionId?` for a read-only pinned projection and do not change persisted selection. A wireframe version belongs to the supplied flow (or current flow if omitted). Offline HTML provenance includes document revision, flow name/number, and wireframe name/number. Tablet is an allowed device, with 768×1024 minimum canvas; desktop and mobile remain supported. AI guidance explicitly permits tablet and copying suitable existing same-device navigation while preserving unrelated page body content; it does not imply live sharing between copies.

Original-service semantics and actual provider quality remain separate evidence. No real Groq call or original-service mutation was performed for these changes.

## Phase 5 — persisted page jobs and automatic shared navigation

New wireframe `append` and `regenerate` requests now create persisted page jobs. Existing `edit` requests and older runs/proposals retain their previous behavior. `AiRun.pageTasks?` contains `WireframePageTask` objects: `{id, pageId: string|null, screenIds: string[], label, status, attempt, error, output, screens: WireScreen[]|null}`. Task status is `queued | running | succeeded | failed | cancelled`; attempt counts actual provider starts, from zero before the first call to a maximum of three. `AiRun.pageSummary?` and `Proposal.pageSummary?` are `{total, succeeded, failed, cancelled}`. `Proposal.partial?` explicitly labels incomplete results.

Append creates one task for each requested missing flow page. Regenerate expands screen/page selectors into page tasks, grouping selected screens on the same linked page; each unlinked manual screen gets its own task. Empty regenerate scope means all existing source screens, or all flow pages when there are no source screens. It does not delete existing screens. The provider must return every selected existing screen with its original ID; malformed, omitted, renamed-ID or out-of-page results fail only that task. Successful replacements and new screens use the current validated nested schema. Page calls run sequentially within a run. There is no automatic provider retry.

Each run captures `baseProjectRevision`, `baseFlowRevision`, `baseWireframeRevision`, both originating version IDs, model, mode and selection. The immutable project revision snapshot supplies the same original source data to every initial/retry call. Each provider prompt has `pageTask: {id,pageId,screenIds,label,attempt}`, narrowed `entityIds`, the captured project projection, and `completedScreens` for already successful pages. It never receives another independent history. Navigation targets may reference source screens, already completed screens, or screens returned by the current task; a dangling future target fails that task while preserving earlier results. Keeping original screen IDs prevents a later successful replacement from invalidating earlier links.

Tasks persist their own streamed output, error and validated screen result. Successful results remain available even when another page fails, the user cancels, or the process restarts. A normal terminal run with at least one success has legacy-compatible `status: 'succeeded'`, with explicit partial counts when other tasks failed; zero successes produces `status: 'failed'`. Restart marks queued/running tasks cancelled, preserves completed task payloads and their attempt counts, and performs no provider call. Cancelling similarly marks unfinished tasks cancelled and ignores any late provider result. Cancellation never automatically creates a proposal.

Activity returns the latest 50 runs and latest 100 proposals plus any older current proposals referenced by those returned runs. The combined proposal list is deduplicated and sorted newest first (ID tie-break), so retries cannot displace an active review or approved-result link. Missing proposal records are not fabricated, and references never pull another project's data into the response.

| Endpoint | Semantics |
|---|---|
| POST `/api/ai/runs/:id/retry-pages` `{pageTaskIds?: string[], commandId: string}` | Retry only failed/cancelled tasks below three attempts; omission selects all eligible failed/cancelled tasks. Returns the same AiRun, HTTP 202. Successes are reused without new provider calls. |
| POST `/api/ai/runs/:id/prepare-proposal` `{commandId: string}` | Explicitly prepare a review from retained successes after cancellation/restart. No provider call. Requires a terminal run and at least one success. Returns AiRun with proposalId, HTTP 200. |
| POST `/api/proposals/:id/resolve` | Adds `allowPartial?: boolean`; approving a partial proposal requires explicit `true`, otherwise HTTP 409 `PARTIAL_APPROVAL_REQUIRED`. |

Retry and prepare commands are idempotent. Replay returns the run's current state without scheduling another attempt or creating another proposal. Conflicting command payloads return `COMMAND_CONFLICT`. Before any mutation, retry checks that the run is terminal, no result from this run was applied, the origin is selected/active, both captured artifact revisions still match, and the configured model still matches. Failure leaves outputs, attempt counts and the old proposal unchanged. A permitted retry cancels the prior pending candidate before scheduling work and later emits a new proposal ID; approving an old review returns `PROPOSAL_CANCELLED`. Retry after any applied result returns `RUN_ALREADY_APPLIED`; a new request may be started from the approved result instead. This prevents approval/retry races from producing duplicate destinations.

Every prepared candidate is one aggregate wireframe change. Partial candidates replace only successful page screens and preserve failed/cancelled/unselected source screens. Approval atomically validates the latest source context/revisions and references, creates/selects one new wireframe version, records resultWireframeVersionId and resolution/idempotency state, and leaves the source history untouched. There is no partial write into the active source. Existing partial-approval behavior for legacy per-screen edit proposals is unchanged.

`WireScreen.navigationSync?` stores explicit one-way bindings for `header`, `sidebar` and `footer`. Each optional binding is `{sourceScreenId, sourceElementId, elementIdMap: Record<sourceElementId,targetElementId>}` with at most 500 IDs. Bindings stay within one wireframe version, have one source per region, and cannot form same-region chains/cycles. The shared helper materializes source changes into followers using stable mapped target IDs, leaving their independent body content intact. Linked follower controls are read-only until detached; server canonicalization also prevents a saved follower from diverging. Static copying remains available and removes bindings for the copied regions.

Manual wireframe saves, AI candidate preparation and AI commits synchronize only the selected/new destination's materialized screens, then validate the complete project. Other history versions remain unchanged. Deleting a previously valid source screen/region detaches followers while retaining their last materialized content. New bindings must connect the same device type; changing either screen's device detaches an existing valid binding and preserves its last content. Crafted cross-device bindings are rejected on save/import. Invalid new metadata, cycles, ID collisions and invalid references are rejected. Backup import validates the complete metadata, and project copy/import remaps sourceScreenId, sourceElementId, and every map key/value consistently across all histories. Manual wireframe copies keep their scoped IDs and metadata. Offline HTML and PNG render the materialized saved content.

The AI screen output schema omits navigationSync: the model cannot establish or replace synchronization ownership. Existing bindings are retained by screen ID and applied by the server. For partial generation, a successful source update may intentionally synchronize unselected nonfailed followers. If that propagation would alter a failed/cancelled screen, the new candidate instead restores that screen's exact original elements/body and detaches its navigation bindings; `Proposal.navigationDetachedScreenIds` identifies affected screens for explicit review disclosure. The original version, including all its bindings, remains unchanged.

Phase 5 adds ten backend tests for sequential partial jobs, failed-only bounded/idempotent retry, stale candidate invalidation, explicit partial approval, cancel/late-result/prepare, restart reuse, source guard ordering, approve/retry races, failed-follower protection, all-history binding remapping and current-proposal retention beyond the activity-history cap. These use injected providers only. No real Groq call or original-service mutation was performed in this phase.

## Phase 6 — local common-navigation inference

`inferNavigationCandidates(screens)` is a bounded, deterministic local analysis. Its result contains an exact `snapshotKey`, reviewed candidates and per-region exclusion reasons. It compares same-device header/sidebar/footer trees by ordered structure, exact text, style, table data and action destinations. Element IDs are ignored for comparison; internal modal references use structural paths. Missing styles and empty children normalize only where they have the same meaning. Explicit style defaults, different actions/destinations or text remain distinct.

The sole existing owner of an equivalent region is preferred as its source; otherwise the first matching screen in document order is proposed. Existing followers are not reassigned. Multiple established owners, duplicate regions, empty templates, external/cross-region modal references and invalid targets are excluded. Inference does not invent missing navigation or call a model.

`applyNavigationInference(screens, analysis, selections)` accepts `{candidateId,targetScreenIds}[]`. It requires the exact analyzed snapshot, recomputes valid candidates and ID maps, validates every choice, and then adds bindings to existing trees. Invalid/stale/duplicate selections fail before mutation. It uses existing element IDs instead of copying regions, preserving body-to-navigation modal references. Existing save/revision/context guards, per-screen undo, version isolation, backup remapping and server synchronization remain applicable. Analysis itself never saves; the dialog requires explicit application and blocks stale snapshots until reanalysis.

`WireScreen.navigationInferenceExcluded?: boolean` is an optional backward-compatible user setting; true excludes the screen as both source and target from new inference. It does not hide content or remove existing explicit bindings. It persists through normal saves, version copies, backups and import. AI edit and page-job output schemas omit this setting; the server restores it from the original screen ID. New generated screens cannot set it. No database version bump or new endpoint is required.

The editor bounds element text to 4,000 characters before creating a new draft/history entry. Its content field has the same native input bound and displays the current count. Original-service inference policies remain unknown; local comparison and review rules are independent design.
## Phase 7 — reviewed extended navigation inference

`inferNavigationCandidates(screens, {extended?: boolean})` preserves exact-only matching by default. The analysis records `{options:{extended:boolean}}`; apply validates those options and recomputes all candidates, maps, differences and source previews. Caller-supplied previews and mappings are never trusted for mutation.

Extended candidates have per-target `kind` (`exact`, `similar`, `missing`, `generated`), `differences` and `destructive`. Similarity requires identical ordered structure, actions, destinations, modal paths, non-menu text and table data. Only labels of navigation-bearing menu elements and styles of layout/menu nodes may differ. Application keeps existing target IDs and internal/body modal references. Missing-region proposals require a single compatible source family; existing empty regions are not treated as absent. Generated headers require at least two eligible same-device screens with no page-level header/sidebar/footer; labels and destinations come only from existing screen names and IDs. Source creation is explicitly disclosed.

Selections add `allowChanges?:boolean`. Every selected nonexact target requires true. The UI leaves these targets unchecked and separately requires review acknowledgment; changing selections, mode or reanalysis clears it. Fresh element IDs are allocated for new regions only. Duplicate UID exhaustion, limits, invalid references, stale input and invalid choices fail atomically without modifying any original screen. Existing exclusions, one-way ownership, version scope and save guards remain applicable. These rules are local design and do not claim equivalence with the original service's private inference.
