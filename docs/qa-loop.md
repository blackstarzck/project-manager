# 독립 검수 loop

## 운영 규칙

검수 담당은 애플리케이션 구현 파일을 수정하지 않는다. 구현 담당의 자체 검사 이후 독립 검수자가 같은 빌드를 브라우저와 저장 데이터로 확인한다.

1. 기능의 기대 동작과 오류 시 보존할 데이터를 먼저 정한다.
2. 구현 담당이 타입 검사 및 해당 단위 검사를 실행한다.
3. QA가 고정된 한국어 예제와 독립된 테스트 데이터 디렉터리로 검사한다.
4. 실패하면 결함 ID, 재현 순서, 기대/실제 결과, 심각도, 담당자, 증거를 기록한다.
5. 구현 담당이 수정하고 QA가 원래 실패 사례와 인접 회귀 사례를 재실행한다.
6. 같은 결함이 세 번 수정 후에도 남으면 원인/설계를 재검토한다.
7. 단계별 필수 시나리오, 데이터 손실 및 핵심 작업 차단 결함 0건, 관련 회귀 검사 통과 시 다음 단계로 진행한다.

기능 실행 결과(`TESTED`, `PARTIAL`, `BLOCKED`, `NOT_IMPLEMENTED`)와 원본 근거(`OBSERVED`, `DOCUMENTED`, `INFERRED`, `UNKNOWN`)는 별도로 기록한다. 기능 테스트 통과는 원본 화면 일치를 의미하지 않는다.

## 공통 예제

- 프로젝트: `동네 도서관 예약 서비스`
- 사용자: 도서관 회원과 사서
- 주요 흐름: 도서 검색 → 상세 정보 → 예약 → 예약 내역
- 검수 문구: `예약 취소는 수령 예정일 전날까지 가능합니다.`
- 비밀정보: 자동 검사에서 실제 API 키/프로덕션 `.env`를 읽거나 출력하지 않는다. AI 회귀 검사는 테스트 프로세스에만 주입된 공급자를 사용한다. 실제 Groq 연결 검증은 별도 수동 smoke 결과로만 기록한다.
